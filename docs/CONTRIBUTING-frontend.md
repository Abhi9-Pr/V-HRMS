# Adding a feature to Vespera.Client

This is the Angular equivalent of `docs/CONTRIBUTING-slices.md`. `features/departments/` is the
reference implementation — when in doubt, copy its shape. This document assumes you've read
`AGENTS.md` at the repo root.

## Folder layout

```
Vespera.Client/src/app/
  core/                    auth, HTTP interceptors, guards, the generated API client, cross-app
                           services (theme, loading, notifications) — see below.
  shared/                  the UI kit: data table, form-error, confirm-dialog, empty/error/loading
                           states, file uploader, date-range picker, currency/date pipes,
                           permission-button. Nothing feature-specific lives here.
  shell/                   the app chrome: sidenav, topbar, breadcrumb, global search, error pages.
  features/<name>/
    <name>.routes.ts        lazy Routes, `data: { permissions, breadcrumb }` on each route.
    <name>.nav.ts            one NavItem — see "Routing and the sidenav" below.
    data/<name>.facade.ts    wraps the generated API client; see docs/frontend-state.md.
    <screen>/<screen>.component.ts (+ .html)
```

Copy `features/departments/*` file-for-file as your starting point for a new feature; rename,
then adjust the aggregate-specific bits. Every screen follows the same shape: a facade with
signals, a component that reads them, `<vespera-data-table>`/`<vespera-permission-button>` from
`shared/` instead of hand-rolled equivalents.

## The generated API client, and the shared library it lives in

As of the mobile-hardening phase (see AGENTS.md), everything an app-shell needs to talk to the API
and manage a session — the generated client, `AuthService`, `TokenStorageService`, interceptors,
`permission.util.ts` — lives in `Vespera.Client/projects/vespera-shared`, a buildable Angular
library published locally as the `vespera-shared` import specifier (path-mapped in `tsconfig.json`
to the built `dist/vespera-shared`, so it must be built — `ng build vespera-shared` — before
anything that imports it). `Vespera.Mobile` consumes the exact same library rather than forking
any of this logic; only UI is app-shell-specific. One exception: `TokenStorageService` is an
abstract port in the shared library, and each app-shell registers its own concrete
implementation in `app.config.ts` — Vespera.Client uses sessionStorage (see "Auth and tokens"
below), Vespera.Mobile uses platform secure storage (Keychain/Keystore) once that phase lands.

`projects/vespera-shared/src/lib/api/generated/api-client.ts` is generated by NSwag from
`Vespera.Api/openapi.json` — **never hand-edit it**; regenerate it instead. Feature code never
imports it directly either — a facade wraps it (see docs/frontend-state.md), so a regeneration
only ever touches facades, not components.

```bash
dotnet build Vespera.Api          # regenerates Vespera.Api/openapi.json
cd Vespera.Client
npm run api:generate              # regenerates projects/vespera-shared/src/lib/api/generated/api-client.ts from it
ng build vespera-shared           # rebuilds the library so consuming apps pick up the change
```

Every generated `*Client` class ships with a bare `@Injectable()` (no `providedIn: 'root'`), so
each one must be listed once in `vespera-shared`'s `api-config.provider.ts`'s
`provideVesperaApiClients(apiBaseUrl)` — forgetting this only fails at runtime
(`NullInjectorError`), not at build time. Add a new feature's client to that list the same day you
add its facade. `apiBaseUrl` is passed in by each app-shell's own `environment.ts` rather than
imported directly, since Vespera.Client and Vespera.Mobile point at different hosts.

If a controller action doesn't have an explicit `[ProducesResponseType(typeof(X), 200)]`
attribute, NSwag generates `Observable<void>` for it regardless of what the action actually
returns — `ToActionResult(this)`'s return type is `IActionResult`, which erases the real payload
type from Swashbuckle's reflection. Any new endpoint with a JSON response body needs that
attribute for the generated client to be useful at all.

## Routing and the sidenav

Each feature's `<name>.routes.ts` sets `data: { permissions: [...], breadcrumb: '...' }` on its
routes, and its sibling `<name>.nav.ts` exports one `NavItem` with the *same* permissions value.
`core/navigation/nav-tree.ts` assembles `NAV_TREE` from every feature's `NavItem` — this is what
"route-driven navigation" means here: there's no separately-maintained sidenav config that can
drift from what a route actually requires, because both read from the same constant
(`core/authorization/permissions.ts`, which mirrors the backend's `Permissions` catalog — add a
new permission to both places, never as a bare string in either).

## Permission checks — three call sites, one function

`core/auth/permission.util.ts`'s `hasPermission(granted, required)` is the single implementation
`permissionGuard`, `*vesperaHasPermission`, and `<vespera-permission-button>` all call. Use:

- `canActivate: [permissionGuard]` + `data.permissions` on a route — hides an entire screen.
- `*vesperaHasPermission="'Departments.Manage'"` — hides an arbitrary chunk of template.
- `<vespera-permission-button [permission]="Permissions.Departments.Manage">` — hides (not just
  disables) a single action button; prefer this over a raw `mat-button` for anything
  permission-gated, so the check is never accidentally skipped.

## Auth and tokens

`AuthService` is the only thing that reads or writes a token. The access token lives **in
memory only** (never persisted — a page reload always goes through `tryRestoreSession()`, which
uses the refresh token). The refresh token lives in `sessionStorage`, not `localStorage` — see
`TokenStorageService`'s doc comment for why (in short: httpOnly cookies would be better, but the
API doesn't issue them yet; sessionStorage is the pragmatic middle ground until it does).

`authInterceptor` attaches `Authorization: Bearer <token>` once signed in, and only falls back to
the pre-auth `X-Tenant-Id` header (via `TenantResolutionService`) when there's no session yet —
login, tenant lookup. **Do not** attach both on an authenticated request "just in case" — the API
prefers the JWT's own `tenant` claim once one exists, and an integration-test helper doing exactly
this (leaving `X-Tenant-Id` on every request, including post-login ones) once masked a real bug
where the server-side tenant context was being resolved before authentication ran. If you're
writing a test helper that builds an authenticated `HttpClient`, don't carry a tenant header
forward past login — let the JWT do its job so the test actually exercises what a real client does.

## Design tokens

Every color, spacing, or shadow value in `shared/`, `shell/`, or a feature component must
reference a token (`var(--vespera-color-primary)`, or via Tailwind's `bg-primary`/`text-danger`/
etc. utility classes — `tailwind.config.js` maps its palette to the same CSS custom properties).
Never hardcode a hex color or a raw `px` spacing value in a component stylesheet. See
`src/styles/tokens.css` (light) / `tokens.dark.css` (dark, keyed off `[data-theme="dark"]`) for
the full token list, and `src/styles/material-theme.scss`'s header comment for why Angular
Material's own M3 palette is a *separate* set of values kept in sync by hand, not derived from
the tokens automatically.

## A content-projection gotcha worth knowing before you build another wrapper component

`<vespera-permission-button>` wraps three different Angular Material button variants
(`mat-flat-button`/`mat-stroked-button`/`mat-icon-button`, chosen by an `@switch`) and needs the
same projected content (`<ng-content>`) inside whichever one renders. A naive version with one
`<ng-content>` per `@case` branch silently drops the projected content — Angular does not reliably
distribute projected content across multiple unnamed `<ng-content>` outlets living in mutually
exclusive `@if`/`@switch` branches. The fix (see `permission-button.component.html`): capture the
projected content **once**, in an `<ng-template #content><ng-content /></ng-template>`, then
render it into whichever branch is active via `<ng-container *ngTemplateOutlet="content" />`. Any
future wrapper component that conditionally renders one of several host elements around
`<ng-content>` needs this same pattern.

## Testing

- **Unit tests**: Jest, colocated as `<file>.spec.ts` next to the file under test (not a parallel
  `__tests__/` tree). `npm test`. A facade test mocks the generated client (see
  `departments.facade.spec.ts`) — never mock `HttpClient` directly in a facade test, and never let
  a component test make a real HTTP call. A component that opens a `MatDialog` mocks `MatDialog`
  itself (`{ open: jest.fn() }`), not the dialog component it opens.
- **E2E**: Playwright, under `Vespera.Client/e2e/`, `npm run e2e`. `e2e/playwright.config.ts`
  deliberately has no `webServer` block — it expects both halves of the stack already running (see
  below), the same way a person testing the app manually would. A spec that needs real seeded data
  (like `departments.spec.ts`) checks `/health/live` in a `beforeEach` and calls `test.skip()` if
  the API isn't reachable, mirroring the backend's own Docker-probe-skip pattern — it fails loud
  when the API *is* up and something's actually broken, and skips quietly rather than red-herring
  failing when it just isn't running.

## Running the app against the real API

```bash
# Terminal 1
dotnet run --project Vespera.Api          # ASPNETCORE_ENVIRONMENT=Development picks up
                                            # appsettings.Development.json automatically via
                                            # launchSettings.json; https://localhost:7095

# Terminal 2
cd Vespera.Client
npm start                                  # http://localhost:4200
```

On first login, the form asks for a **tenant code**, not a tenant GUID — it resolves the GUID
itself via `GET /api/v1/tenants/by-code/{code}` (anonymous, rate-limited like the rest of auth).
